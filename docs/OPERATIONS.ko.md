# 운영 설정 안내

## 생일 표시 추가 업데이트 (2026-10-21)

이전 회원·뉴스레터 버전을 이미 적용한 경우, 새 코드 배포 전에 다음 명령만 추가 실행합니다.

```bash
npm run db:upgrade:birthday
npm run db:generate
```

원본 개인 블로그에서 처음 업데이트한다면 아래 `npm run db:upgrade`가 회원·뉴스레터 SQL과 생일·댓글 계정 연결 SQL을 함께 실행합니다. 새 DB는 `db:init`가 전체 스키마를 만듭니다. 생일 컬럼은 선택 값이므로 기존 회원·글·댓글을 삭제하지 않습니다.

회원가입에서 생일을 입력하거나, 로그인 후 내 계정의 ‘생일과 작성 당시 나이’에서 추가·수정·삭제합니다. 생일을 바꾸면 그 회원이 쓴 기존 글과 연결된 댓글도 다시 계산합니다.

표시 기준은 **작성 당시 한국 날짜 − 생일 + 1일**입니다. 태어난 날은 1일이고 한국 시간 자정에 일수가 바뀝니다. 현재 나이를 모든 과거 글에 똑같이 표시하지 않습니다. 일수는 `(7305 일)`과 같은 형식입니다. 글 목록·상세·인기 글·검색·관리 화면·댓글·답글·댓글 알림·뉴스레터·텍스트 다운로드·인스타 이미지에 공통 적용합니다. 이미 발송된 뉴스레터의 스냅샷은 바꾸지 않습니다.

생일이 없는 회원, 작성자가 연결되지 않은 과거 글, 기존 익명 댓글·새 비회원 댓글은 `(생일 미등록)`으로 표시합니다. 회원 댓글은 서버에서 로그인 계정으로 연결하며, 요청에 다른 사람의 이름·회원 ID·생일을 넣어도 그 사람의 계정이나 나이로 기록되지 않습니다. 과거 익명 댓글을 이름만 보고 회원 계정에 연결하지 않습니다.

기존 글도 관리자 생일 기준으로 표시하려면 관리자가 생일을 등록하고 `npm run db:claim-legacy`로 해당 관리자에게 작성자 미지정 글을 귀속시킵니다. 원래 운영자 생일을 코드에 고정한 방식은 제거했습니다.

## 1. 기존 블로그에 적용

원본 소스는 그대로 보관하고 이 수정본으로 교체합니다. 게시물은 소스 ZIP이 아니라 기존 PostgreSQL에 저장되어 있으므로 같은 `thinkstorage_DATABASE_URL`을 유지해야 합니다.

Node.js 20.9 이상, PostgreSQL 연결, Vercel 배포 프로젝트가 필요합니다. 패키지는 `npm install`로 설치합니다. 이번 작업 환경은 패키지 다운로드가 차단되어 잠금 파일을 만들지 못했습니다. 설치가 성공하면 생성된 `package-lock.json`도 저장소에 포함하고 이후 설치에는 `npm ci`를 사용하세요.

`.env.example`을 `.env`로 복사합니다. 실제 `.env`·API 키는 Git에 올리지 않습니다. Vercel 환경변수에도 같은 이름과 값을 설정합니다.

### 기존 DB가 있는 경우

기존 DB 백업 후 다음 명령을 실행합니다.

```bash
npm run db:upgrade
npm run db:generate
```

`db:upgrade`는 기존 `Post` 테이블이 있는 DB용입니다. 새 회원·세션·구독·투고 테이블과 `Post.authorId`를 추가하며 원래 글·댓글·카테고리를 삭제하지 않습니다. SQL 전체는 하나의 트랜잭션입니다. 실행 권한이 없는 DB 연결이라면 제공한 SQL을 해당 DB의 관리용 SQL 편집기에서 실행합니다.

### 새 빈 DB인 경우

```bash
npm run db:init
```

기존 DB에 대해 `migrate reset`이나 데이터 삭제 옵션을 실행하지 않습니다. 이 프로젝트는 과거 마이그레이션 이력이 제공되지 않아 기존 DB용 추가 SQL과 새 DB용 `db push`를 구분했습니다.

### 검사 및 배포

```bash
npm run typecheck
npm test
npm run build
```

기존 GitHub/Vercel 프로젝트에 수정본을 올리고 배포합니다. Vercel은 `npm run build`를 사용하며 DB 스키마 수정은 빌드 전에 적용해야 합니다. 이번 작업에서는 실제 운영 DB·Vercel 프로젝트에 접근하거나 배포하지 않았습니다.

## 2. 최초 관리자와 집필자

환경변수 두 개를 설정합니다.

| 이름 | 값 |
| --- | --- |
| `ADMIN_EMAIL` | 본인 관리자 이메일, 예: owner@example.com |
| `ADMIN_SETUP_TOKEN` | 관리자 초기 설정용 무작위 문자열 |

무작위 값 생성 예시는 다음과 같습니다. 초기 설정 키와 Cron 키는 각각 다른 값으로 만듭니다.

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

1. 배포 후 `/register` 접속.
2. `ADMIN_EMAIL`과 같은 이메일, 이름, 12자 이상 비밀번호 입력.
3. ‘사이트 최초 관리자 설정’을 열고 `ADMIN_SETUP_TOKEN` 입력.
4. 관리자 계정으로 `/admin/dashboard` 접속.
5. 다른 사람이 회원가입하면 회원 목록에서 직책을 집필자로 변경.

이메일과 설정 키가 모두 맞고 아직 관리자가 없을 때만 최초 관리자가 됩니다. 가입 폼에 `role`을 임의로 보내도 권한을 얻지 못합니다. 일반 회원은 항상 독자로 시작합니다. 최초 설정 후 `ADMIN_SETUP_TOKEN`을 제거하고 재배포할 수 있습니다.

기존 글에는 작성자가 없으므로 기본적으로 ‘기존 글’로 표시하며 관리자만 수정할 수 있습니다. 관리자에게 귀속시키려면 관리자 가입 후 로컬 `.env`를 준비하고 실행합니다.

```bash
npm run db:claim-legacy
```

이미 작성자가 있는 새 글은 변경하지 않습니다. 집필자는 본인 글만 수정할 수 있고 삭제는 관리자에게 요청합니다. 공개 글 읽기·기존 익명 댓글은 회원가입 없이도 가능합니다. 계정 비밀번호 재설정·변경 화면은 이번 범위에 포함하지 않았습니다.

## 3. 뉴스레터 연결

Resend 계정에서 발신 도메인을 인증하고 발신·수신 API에 필요한 권한의 API 키를 발급합니다. 발신만 사용할 때는 투고용 수신 도메인이 필요하지 않습니다.

| 이름 | 예시 / 설명 |
| --- | --- |
| `RESEND_API_KEY` | Resend API 키 |
| `EMAIL_FROM` | 함께 쓰는 블로그 <newsletter@example.com> — 인증된 발신 도메인 |
| `SITE_URL` | https://your-blog.vercel.app — 경로·쿼리 없는 실제 HTTPS 주소 |
| `CRON_SECRET` | 별도로 생성한 무작위 비밀값 |

`EMAIL_FROM`에는 Resend의 발신 도메인 인증이 완료된 주소를 사용합니다. `SITE_URL`은 메일의 원문 링크·수신 거부·이메일 확인 링크에 사용합니다. 테스트 환경과 운영 환경을 혼동하지 마세요. 값이 빠져 있으면 UI에 미설정 상태를 표시하고 메일 API는 503을 반환합니다.

### 회원 수신 동의

1. 회원이 `/account`에서 뉴스레터 신청.
2. 등록한 이메일로 확인 링크 수신.
3. 링크를 열어 ‘이메일 확인 및 수신 동의’ 버튼 클릭.
4. 그 후 생성되는 주간 묶음부터 수신.

확인 링크는 24시간 유효하며, 단순히 링크를 여는 것만으로 구독되지 않습니다. 확인 전에는 뉴스레터를 발송하지 않습니다. 내 계정에서 해제하거나 메일 하단의 수신 거부 링크를 사용할 수 있습니다. 구독을 해제하면 대기 중인 배송에서도 제외합니다. 다시 신청할 때는 다시 확인합니다.

### 자동 실행

기본 `vercel.json`은 매일 UTC 00:00에 다음 주소를 호출합니다.

```text
GET /api/cron/newsletter
Authorization: Bearer <CRON_SECRET>
```

Vercel에 `CRON_SECRET`이 설정되어 있으면 Cron 호출의 인증 헤더를 사용합니다. Vercel 외부 스케줄러도 이 헤더를 보내도록 설정하면 됩니다. 별도의 스케줄러는 이 수정본이 생성하거나 계정에 등록하지 않습니다.

기본값은 한국 09시경 일별 실행이며, 주당 한 묶음만 생성하므로 정상 운영 시 월요일 아침 뉴스레터가 발송됩니다. 수동 발송·누락된 실행 뒤의 첫 처리 시점에는 요일이 달라질 수 있습니다. Vercel Hobby는 하루 한 번의 Cron만 지원하고 실행 시각에 오차가 있으므로 정확한 09시 배송을 보장하지 않습니다. 시간별 처리가 가능한 요금제에서는 `vercel.pro.example.json`의 설정을 `vercel.json`에 적용하거나 외부 스케줄러를 사용합니다.

관리자는 대시보드에서 발송 후보·배송 현황을 보고 이번 주 묶음을 수동 발송하거나 미완료 건을 이어서 처리할 수 있습니다. 수동 발송 버튼은 실제 메일을 발송합니다.

### 묶음과 재시도 방식

- 여러 작성자의 아직 소개되지 않은 공개 글을 오래된 순으로 최대 30편 묶습니다. 제목·작성자·320자 내외 요약·전체 글 링크를 보냅니다.
- 첫 발송에는 기존 공개 글도 후보가 됩니다. 과거 글을 제외하려면 운영 전에 후보 선택 정책을 바꿔야 합니다.
- 발송 당시 확인·동의한 구독자만 해당 묶음의 수신자로 고정합니다. 이후 가입자는 다음 묶음부터 받습니다.
- 한 실행에 최대 40명을 처리합니다. 40명 초과 수신자는 이후 실행 때 이어서 처리합니다.
- 발송 이력과 수신자별 동일 요청 키를 저장합니다. 이미 발송한 이메일은 자동 재발송하지 않습니다.
- 제공자가 발송을 접수했는지 불분명한 경우 23시간 안에만 같은 요청으로 재시도합니다. 그 이후에는 중복 방지를 위해 중단하고 관리자에게 기록을 표시합니다. 기본 일별 실행만으로는 그 시간 안에 재시도하지 못할 수 있으므로 관리자 재시도 또는 시간별 실행이 필요합니다.
- `SENT`는 제공자가 요청을 접수했다는 의미입니다. 수신함 도착·열람을 뜻하지 않으며 반송·스팸 분류는 Resend 기록에서 확인합니다.
- 묶음 생성 후 포함된 글을 삭제·비공개 전환하면 아직 보내지 않은 해당 묶음 배송을 취소합니다. 이미 보낸 메일은 회수하지 못합니다. 묶음 자체의 내용은 재시도 중 바꾸지 않습니다.

## 4. 이메일 투고 연결

뉴스레터와 같은 Resend API 키를 사용할 수 있으며 수신 메일 조회 권한도 필요합니다.

1. Resend의 Receiving에서 수신 도메인을 준비합니다. 계정에서 제공하는 `<id>.resend.app`도 사용할 수 있습니다.
2. 자체 도메인은 `inbound.example.com`처럼 별도 서브도메인에서 Receiving을 활성화하고 Resend에 표시된 MX 레코드를 DNS에 추가합니다. 기존 업무용 메일의 MX는 유지합니다.
3. Resend Webhooks에서 다음 URL을 등록하고 `email.received` 이벤트 선택.
4. 표시된 서명 키를 `RESEND_WEBHOOK_SECRET`에 입력하고 재배포.

```text
https://your-blog.vercel.app/api/webhooks/email
```

| 이름 | 설명 |
| --- | --- |
| `INBOUND_EMAIL_DOMAIN` | inbound.example.com 또는 계정의 수신용 `<id>.resend.app` 도메인, @ 없이 입력 |
| `RESEND_WEBHOOK_SECRET` | 해당 웹훅의 whsec_ 로 시작하는 서명 키 |
| `RESEND_API_KEY` | 수신 메일 조회 권한이 있는 API 키 |

### 집필자 사용법

1. 집필자 계정으로 `/account`의 ‘이메일로 글 올리기’에서 전용 주소 생성.
2. 표시된 `submit+무작위문자열@수신도메인` 주소를 복사해 보관. 주소 전체는 생성 직후 한 번만 표시합니다.
3. 회원가입에 사용한 발신 이메일에서 그 주소로 새 메일 작성.
4. **메일 제목 → 글 제목**, **일반 텍스트 본문 → 글 본문**. 자동으로 ‘이메일 투고’ 카테고리에 공개 게시됩니다.

마크다운은 기존 글 렌더러가 처리합니다. HTML 서식·첨부 사진·PDF·워드 파일은 가져오지 않습니다. 일반 텍스트를 함께 보내는 메일 프로그램을 사용하세요. 본문은 10만 자까지입니다. 회신·전달 메일에 포함된 기존 대화와 서명도 본문으로 게시되므로 새 메일을 쓰는 방식이 적합합니다.

발신자는 등록된 이메일과 일치해야 하고, 수신 서비스가 계산한 DMARC 또는 From 도메인과 정렬된 DKIM 인증을 통과해야 합니다. 전용 주소는 공개하지 말고 유출 시 폐기·재생성합니다. 독자로 강등된 계정의 전용 주소로는 게시되지 않습니다.

전용 주소·발신자·현재 직책·웹훅 서명을 모두 검증하며, 같은 수신 메일 ID가 다시 전달되어도 게시물을 중복 생성하지 않습니다. ‘내 계정’에서 최근 성공·거절 결과를 볼 수 있습니다. 정상 메일이 거절되면 웹 글쓰기를 사용하고 Resend 수신 인증 상태를 확인하세요.

## 5. 운영 점검

처음 연결한 뒤 실제 테스트 회원 두 명을 만들고 다음을 확인합니다.

- 독자의 글 발행·수정·삭제가 거절되는지.
- 집필자 A가 본인 글을 수정할 수 있고 B의 글 수정과 모든 글 삭제는 거절되는지.
- 관리자의 전체 글 수정·삭제, 직책 변경이 가능한지.
- 수신 확인 전에는 배송되지 않고, 확인 후 한 번 배송되는지.
- 구독 해제 후 대기 중인 메일이 제외되는지.
- 인증된 이메일 투고가 한 번만 게시되고 웹훅 재전달 시 중복되지 않는지.
- 이메일 주소 재생성 후 이전 주소로는 게시되지 않는지.

만료 세션·로그인 제한 기록은 정기적으로 `npm run db:cleanup`으로 정리할 수 있습니다. 만료 세션은 정리 전에도 로그인으로 인정하지 않습니다. 발송 이력·투고 이력은 중복 방지에 사용되므로 임의 삭제하지 않습니다.
